# 手動ベンチマークGitHub Actions設計

## 目的

GitHub Actionsの手動DispatchからWebフレームワーク比較とjs-framework-benchmark準拠比較を実行し、GitHub Actions Summaryで総合ランキング、項目別ランキング、実測値、最速値に対する比率を確認できるようにする。

1回のDispatchで得た結果は、ホスト差や独立実行回数の要件を満たす権威的ランキングではなく、同一ジョブ内で得た参考ランキングとして表示する。既存の統計的権威性に関する契約は変更しない。

## 対象スイート

手動Dispatchに`suite`入力を定義し、次の値から選択する。既定値は`all`とする。

- `all`: 両方のスイートを順番に実行する
- `web-framework`: 既存の`pnpm bench:web-framework`を実行する
- `js-framework`: krausest/js-framework-benchmarkの操作モデルに沿った既存のローカル比較を安定測定条件で実行する

`js-framework`というDispatch上の名前は利用者に比較元を伝えるための名称であり、上流公式ランナーを直接実行することを意味しない。Summaryにはtachyon-domリポジトリ内の比較であることを明記する。

## GitHub Actionsワークフロー

`.github/workflows/benchmarks.yml`を手動Dispatch専用ワークフローとして追加する。ジョブは単一のUbuntuジョブとし、選択されたスイートを順番に実行する。単一ジョブにすることで、同じランナー環境を共有し、Summary集約や成果物受け渡しを単純に保つ。

ワークフローはcheckout、Nodeとpnpmのセットアップ、依存関係の固定インストール、Chromiumと必要なOS依存のセットアップ、出力ディレクトリの準備、ベンチマーク実行、Summary生成、Artifactアップロードを行う。タイムアウトと同一refに対するconcurrencyを明示する。

ベンチマーク結果は自動コミットしない。JSONと生成したMarkdownを、実行IDを含む名前のArtifactとして保存する。ベンチマークまたはSummary生成が失敗した場合も、存在するログと途中成果物は`always()`条件でアップロードする。

## 出力契約

各ベンチマークはワークフロー固有の一時ディレクトリへJSONを出力する。GitHub Actions固有の処理は、入力値と出力パスを既存ランナーへ渡すことに限定する。

TypeScript製のSummary生成器は、選択されたスイートとJSONパスを明示的な引数で受け取り、Markdownを標準出力または指定ファイルへ出力する。JSONの標準出力を解析せず、保存済みの構造化結果だけを入力とする。

Summary生成器は不明なスイート、読めないJSON、期待する測定値の欠落、有限でない数値、比較対象が空の場合に非ゼロ終了する。部分的な表を正常結果として表示しない。

## Summary表示

先頭に次の実行情報を表示する。

- 選択スイート
- commit SHA
- Node、OS、CPUなどJSONに保存済みの実行環境情報
- 「単一Dispatch内の参考ランキングであり、権威的ランキングではない」という注意書き

### Web Framework

既存スコア計算による総合ランキングを表示する。続いて次の項目ごとに独立したランキング表を表示する。

- 静的リクエスト数/秒
- 静的p95レイテンシ
- 動的リクエスト数/秒
- 動的p95レイテンシ
- ストリーミングTTFB
- ストリーミング完了時間
- クライアント遷移時間
- クライアントバンドルサイズ

### js-framework-benchmark準拠比較

操作時間の幾何平均に基づく総合ランキングを表示する。続いて、結果JSONに含まれる各操作シナリオを項目別に表示する。補助指標としてメモリ使用量とバンドルサイズが存在する場合は、それぞれ独立したランキング表を表示する。

各ランキング表には順位、実装またはフレームワーク名、実測値、最速値に対する比率を含める。リクエスト数/秒は大きい値を優位とし、それ以外は小さい値を優位とする。比率は常に`1.000x`が最良となる向きに正規化する。表示精度による見かけ上の同値ではなく、生の有限数値が完全に同じ場合だけ同順位とし、競技順位方式で次順位を飛ばす。

Markdownセルに含まれる制御文字、改行、縦棒は安全に表示できるようエスケープする。

## コンポーネント境界

- ベンチマークランナー: 測定とJSON保存を担当し、GitHub Actionsの表示事情を知らない
- ランキング計算: 指標の向き、順位、最速比、総合値を純粋関数で計算する
- Markdown整形: 計算済みランキングをSummary用Markdownへ変換する
- CLI: 引数、JSON読み込み、検証、ファイル出力、終了コードを担当する
- GitHub Actions: 環境準備、スイート選択、コマンド実行、`GITHUB_STEP_SUMMARY`への追記、Artifact保存を担当する

既存のWeb Framework総合スコア計算とローカル比較の集計ロジックは再利用し、同じ概念を別実装で重複させない。Summary固有の項目別順位計算は純粋関数として分離する。

## テスト戦略

TDDで、Summary生成器とワークフロー契約の失敗テストから追加する。

- 大きい方が良い指標と小さい方が良い指標の順位
- 生値が同一の場合の同順位と次順位
- 最速比の向きとゼロ値の扱い
- 単位と表示精度
- Markdownセルのエスケープ
- Web Framework総合表と全項目表
- js-framework-benchmark総合表、操作別表、補助指標表
- 両スイートを結合したSummary
- 欠損値、非有限値、空の比較対象、不明なスイートの失敗
- `workflow_dispatch`、3つの選択肢、既定値`all`、各実行コマンド、Summary追記、`always()`付きArtifactアップロードを含むワークフロー契約

単体テスト後、両スイートのsmoke相当条件で実際のJSONとMarkdownが生成できることを確認する。起動したブラウザとサーバープロセスが終了したことも検証する。

## 非対象

- GitHub Actionsから結果を自動コミットすること
- 上流の全フレームワークを取得して公式js-framework-benchmarkランナーを実行すること
- 単一Dispatchの結果を権威的または公式なランキングとして扱うこと
- 過去実行との推移グラフやPRコメントを生成すること
- 定期実行やpushイベントで自動実行すること
