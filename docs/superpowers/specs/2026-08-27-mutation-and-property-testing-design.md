# Mutation and Property-Based Testing Design

## Goal

Improve the defect-detection strength of the tachyon-dom test suite by adopting fast-check for property-based testing and StrykerJS for mutation testing across the production TypeScript sources.

## Context

The repository already uses Vitest and contains three bounded, hand-written seeded property suites for compiler whitespace, progressive stream escaping, and benchmark JSON validation. Those suites generate repeatable cases, but they do not shrink failures to minimal counterexamples and each suite maintains its own pseudo-random generation logic.

The existing example-based suite covers many concrete regressions and boundary contracts. It does not currently measure whether assertions detect plausible implementation defects. Mutation testing will provide that signal without replacing existing coverage or example-based tests.

## Scope

This change will:

- add fast-check as a development dependency;
- migrate the three hand-written seeded property suites to fast-check;
- add focused properties for HTML escaping, HTML tag whitespace, URL and redirect policy, and stream composition;
- add StrykerJS with the Vitest runner;
- mutate every implementation file matched by `src/**/*.ts`, excluding `src/tachyon-html.d.ts`;
- use a mutation-specific Vitest configuration that excludes E2E, browser-fixture, benchmark, release, and package-artifact verification suites;
- expose explicit local package scripts for property and mutation testing;
- generate local clear-text, HTML, JSON, and incremental mutation reports;
- capture a baseline mutation score without failing on a score threshold;
- record mutation outcomes and remaining obligations in a local coverage ledger.

This change will not add mutation testing to GitHub Actions, establish a mutation-score failure threshold, remove existing example-based tests, or suppress broad classes of mutants.

## Dependencies and Configuration

`fast-check`, `@stryker-mutator/core`, and `@stryker-mutator/vitest-runner` will be development dependencies. Compatible current versions will be pinned through the existing pnpm lockfile.

`tests/fast-check.setup.ts` will configure a stable default seed and 100 runs per property. `FAST_CHECK_SEED`, `FAST_CHECK_PATH`, and `FAST_CHECK_NUM_RUNS` will allow an explicit local replay or larger campaign. Security-boundary and stream-escaping properties will default to 256 runs when no run-count override is provided. Stryker workers will therefore execute the same generated examples for every mutant instead of receiving time-dependent random inputs.

`vitest.config.ts` will load the fast-check setup for normal test runs. A new `vitest.mutation.config.ts` will preserve the source aliases and Tachyon Vite plugin needed by unit tests while limiting Stryker's dry run and mutant runs to focused unit and property suites. It will exclude tests whose main purpose is E2E browser execution, example application verification, benchmark execution or provenance, release workflows, package artifacts, clean-consumer checks, and bundle-size checks.

`stryker.config.json` will use the Vitest runner, the mutation-specific Vitest configuration, per-test coverage analysis supplied by that runner, bounded worker concurrency, and incremental result storage under `reports/mutation/`. The configuration will initially set `thresholds.break` to `null`. Clear-text output will support terminal use, while HTML and JSON reports will support detailed triage and later automation.

`package.json` will expose:

- `test:property` for the property suites;
- `test:mutation` for the normal incremental mutation run;
- `test:mutation:full` for a forced full baseline or refresh.

Generated mutation reports will be ignored by Git.

## Property-Based Test Design

### Compiler whitespace

Generated cases will combine whitespace policy, semantic context, HTML whitespace form, and surrounding text. The properties will require protected contexts to preserve whitespace, ordinary contexts to follow the selected policy, and the server HTML, client template, and generated stream module to agree on the resulting content.

### Progressive stream escaping

Generated Unicode and attacker-controlled strings will be escaped and split across varying trusted HTML chunk boundaries. The resulting UTF-8 bytes will also be decoded across generated byte boundaries. Parsing the reconstructed HTML must produce only the intended element structure and a text node equal to the parser-normalized input. Shrinking must reduce both the input and split positions when a failure occurs.

### Benchmark JSON validation

Generated field paths and invalid numeric values will be inserted into otherwise valid benchmark envelopes. Validation must reject the value and identify the corresponding baseline path. Valid zero boundaries must continue to produce finite comparison ratios.

### HTML escaping

For arbitrary Unicode strings, parsing escaped output as HTML text must recover the parser-normalized input without creating attacker-controlled elements. Inputs without escapable characters must be returned unchanged. Concrete tests will continue to cover exact entity spelling.

### HTML tag whitespace

Normalization must be idempotent. For generated valid tags, it must preserve quoted attribute values and text-node contents while changing only HTML tag separators. Generated malformed constructs must preserve the original input under the existing fail-closed contract.

### URL, srcset, and redirect policy

Generated control characters, encoded controls, backslashes, protocol-relative prefixes, schemes, origins, element names, and attribute names will exercise the policy boundary. Unsafe structural variants must be rejected, configured origins must remain authoritative for absolute URLs, and case changes to element and attribute names must not change the selected rule. Generators will construct valid and invalid cases directly instead of filtering broad arbitrary strings with excessive preconditions.

### Stream composition

Generated source chunks, framing segments, outlet modes, early returns, and source failures will verify that an `once` outlet enumerates the source once, an `omit` outlet closes without emitting source values, and cleanup occurs at most once after completion, cancellation, or failure.

## Coverage Obligations

The local coverage ledger will assign stable identifiers to these obligations:

- `P-COMP-01`: semantic whitespace contexts preserve required content;
- `P-COMP-02`: compiler output targets agree on whitespace behavior;
- `P-STREAM-01`: arbitrary escaped input cannot leave its intended text node;
- `P-STREAM-02`: chunk and UTF-8 byte boundaries do not change stream meaning;
- `P-BENCH-01`: malformed numeric benchmark fields are rejected with their field path;
- `P-ESC-01`: escaped arbitrary text parses without attacker-created elements;
- `P-WS-01`: tag normalization is idempotent and preserves non-tag semantics;
- `P-WS-02`: malformed HTML is preserved by the fail-closed path;
- `P-URL-01`: structural URL hazards are rejected in raw and decoded forms;
- `P-URL-02`: origin, purpose, element, and attribute rules remain authoritative;
- `P-STREAM-COMP-01`: outlet mode controls source enumeration and output;
- `P-STREAM-COMP-02`: completion, return, and failure close the source at most once;
- `M-SRC-01`: every in-scope production source is classified by Stryker as killed, survived, no coverage, timeout, compile error, or ignored with a documented reason;
- `M-SURV-01`: every security-relevant surviving mutant is either killed by an independent test or retained with a documented equivalent-mutant justification.

Existing example-based tests remain responsible for named regressions, exact error messages, public examples, compatibility behavior, and boundary values. Apparent overlap with a property is intentional when the tests cover different risks or layers.

## Mutation Baseline and Triage

The first forced full run will establish the baseline without a score gate. The generated report will be summarized in the local coverage ledger using Stryker's `Killed`, `Survived`, `NoCoverage`, `Timeout`, and `CompileError` outcomes.

Surviving mutants will be triaged in this order:

1. security and trust-boundary behavior;
2. compiler output correctness;
3. stream lifecycle and cleanup;
4. public runtime behavior;
5. adapters and tooling.

A surviving mutant that represents a meaningful behavior change requires a new assertion, example, or property. The new check must first be demonstrated against that mutant and then rerun against the original implementation. Equivalent mutants may receive a narrow Stryker ignore annotation only after the ledger records why no observable contract can distinguish them. Broad mutator exclusions are out of scope.

`NoCoverage` is coverage debt, not a successful outcome. It will identify production behavior reached only by the excluded integration suites or not reached at all. The baseline report will determine whether a later mutation profile should include additional integration tests.

After important survivors are addressed, a separate design and change will choose `thresholds.break` from the measured baseline and runtime cost. No threshold will be guessed during this adoption.

## Error Handling and Reproducibility

fast-check failures must report the seed, counterexample path, and shrunk counterexample through its standard assertion error. `FAST_CHECK_SEED` and `FAST_CHECK_PATH` will replay the exact failing case without modifying a test file.

Invalid fast-check environment values will fail setup with a descriptive configuration error rather than silently changing the campaign. The stable default seed prevents nondeterministic mutant classification.

Stryker's initial dry run must pass before mutant execution. A dry-run failure is reported as configuration or test debt and must not be presented as a mutation baseline. Interrupted runs may retain incremental results, but only a completed forced full run may establish or refresh the baseline.

Tests will continue to use real implementations rather than mocks. Test processes started by the mutation run must be allowed to exit normally. After interruption or completion, Stryker and Vitest child processes will be checked by PID and command line before any targeted cleanup.

## Documentation and Artifacts

The public project documentation does not need a user-facing feature page because these tools affect repository development only. Developer-facing commands will be documented next to the package scripts or in the contributing guidance available during implementation.

The source-aware coverage ledger and baseline summary will live under `.coverage-ledger/`, which is already ignored by Git. The task work log will live under `docs.local/logs/2026-08-27/`.

## Verification

Focused verification will run after each property migration or survivor-driven assertion. The final adoption must run:

```bash
pnpm test:property
pnpm test
pnpm lint
pnpm build
pnpm test:mutation:full
git diff --check
```

The final report must include the normal test count, property-test count, full mutation outcome counts, mutation score, elapsed mutation time, remaining high-risk survivors, remaining `NoCoverage` debt, and confirmation that no Stryker or Vitest child processes remain.

## Success Criteria

- The existing three seeded property suites use fast-check and retain their original contracts.
- The new property suites cover all obligations listed above and report reproducible shrunk failures.
- A completed Stryker full run classifies every mutable production source in scope.
- The baseline report and coverage ledger distinguish meaningful survivors, equivalent mutants, and no-coverage debt.
- Normal tests, property tests, lint, and build pass independently of mutation testing.
- Mutation testing remains an explicit local command and does not alter GitHub Actions.
- No mutation-score failure threshold is introduced before baseline measurement and survivor triage.
