# Public API Layers

Tachyon DOM exposes three API layers. The root entry is for application code, runtime subpaths are for browser integrations and compiler output, and compiler/server/tooling subpaths are for build and server infrastructure. The package remains experimental, but the contracts below describe which imports are intended to remain compatible within a minor release.

## Compatibility rules

The root entry and named subpaths are the supported import surface. Existing exports are not removed or moved without a deprecation period and a release note. Type-only exports follow the same compatibility rule as value exports.

## Stability tiers

Not every export carries the same promise. The export map below labels each subpath with a layer; the layers group into three tiers with different guarantees. The tier decides what a change to that surface must respect, and what an application may rely on.

| Tier                       | Layers                                                                              | What is guaranteed                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | What is not                                                                                                                                                                                                 |
| -------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Application**            | `application`, `application/browser`                                                | The meaning and signature of `createSignal`, `createMemo`, `effect`, `batch`, `untrack`, `createRoot`, `onCleanup`, `createResource`, `mount`, `hydrate`, `createTemplateComponent`, the template syntax in the [syntax specification](syntax-spec.md), and the observable behavior documented in the [runtime guide](runtime.md). Deprecations are announced one minor release ahead.                                                                                                                         | Bundle sizes, the exact HTML the compiler emits (markers, whitespace), and the identity of internal helpers.                                                                                                |
| **Integration** (advanced) | `toolchain`, `server`, `server/application`, `editor tooling`, `tooling`, `browser` | The documented command, option, and data contracts of the compiler, CLI, Vite plugin, router, adapters, cookies, i18n, env, security helpers, diagnostics, and the browser-only runtime entries that applications may import directly (`runtime/signal`, `runtime/router`, `runtime/mount`, `runtime/component`, `runtime/enhancement`, `runtime/error-boundary`, `runtime/stream-client`, `runtime/keyed-rows`, `runtime/virtual-list`). Breaking changes require a migration guide under `docs/migrations/`. | Unspecified fields of compiler IR and client binding records, and the ordering or shape of generated code.                                                                                                  |
| **Generated-only**         | `generated/browser`, `type declarations`                                            | A module produced by compiler version N runs against runtime version N. The `runtime/*` entries in this tier (`text`, `class`, `event`, `attr`, `form`, `fragment`, `hydrate`, `list`, `list-text`, `list-path`, `conditional`, `conditional-core`, `portal`, `store`) exist so generated code can import them without pulling in the compiler.                                                                                                                                                                | Hand-written calls. Their signatures, DOM path formats, marker comments, and binding record shapes may change in any minor release when the compiler changes with them. Recompile templates when upgrading. |

The generated-only tier is deliberately kept out of the application promise so that size optimizations, hydration marker changes, and new specialized runtime paths do not become breaking changes for applications. If application code needs a capability that is only available through a generated-only entry today, that is a request for an application-tier API, and it should be raised as one rather than solved by importing the generated entry.

Generated modules are compiler artifacts: applications may import their declared `bind`, `render`, `stream`, and metadata exports, but should not depend on private names beginning with `__tachyon`.

The `runtime/*` layer is intentionally low-level. It may accept DOM paths, compiled binding records, and trusted compiler output. Those inputs are not the recommended application-facing abstraction and must not be treated as a sanitizer or a substitute for application validation. Compiler-generated imports use these subpaths directly so a browser bundle can omit TypeScript, OXC, parse5, server, and language-server code.

## Common application imports

Use the root entry for ordinary application code:

```ts
import { createResource, createSignal, mount, type Resource, type Signal } from "tachyon-dom";
```

Use an explicit subpath when the code is compiler-generated, low-level, server-only, or tooling-specific:

```ts
import { mountKeyedList } from "tachyon-dom/runtime/list";
import { compileTemplate } from "tachyon-dom/compiler";
import { html } from "tachyon-dom/server/html";
```

Do not import from `dist` files directly. The `package.json` export map is the compatibility boundary and is checked by `pnpm check:exports`, `pnpm verify:package`, and the clean-consumer verification.
