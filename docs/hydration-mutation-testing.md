# Hydration mutation testing

Run `pnpm test:mutation:hydration` to repeat the focused compiler and conditional-runtime campaign. Reports are written to `reports/mutation/hydration/`. This supplements `pnpm test:mutation:full`; it does not measure the entire repository or replace the production browser suite.

The configuration retains the 236 mutations in the reviewed source ranges from commit `478a0d2`. When those functions move, update the ranges and review the mutant inventory before comparing scores. No surviving mutation is suppressed. Incremental reuse is disabled so that each run verifies the current tests.

## Coverage obligations

The tests use the real runtime, hydration scheduler, signals, error handlers, and ownership cleanup. The fixture's hydration wrapper only records handles returned by the actual boundary factory.

| Contract                                                                                   | Tests                                                                               |
| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| Runtime setup declarations, type declarations, and anonymous export diagnostics            | `sfc-import-bindings.test.ts`                                                       |
| Independent eager, load, sibling, and nested hydration boundaries                          | `conditional-hydration-contracts.test.ts`                                           |
| Subscription handoff failures, batched rollback, and immediate retry from an error handler | `conditional-hydration-contracts.test.ts`, `conditional-hydration-rollback.test.ts` |
| Ref release, stale event removal, and nested subtree cleanup                               | `conditional-hydration-contracts.test.ts`                                           |
| Empty SSR text materialization, subsequent updates, and branch removal                     | `conditional-hydration-contracts.test.ts`, `hydration-deferred-updates.test.ts`     |
| Fragment boundary discovery, omitted paths, missing markers, and duplicate markers         | `conditional-hydration-contracts.test.ts`                                           |
| Prepared anchor node counts and sibling paths                                              | `runtime-mount.test.ts`                                                             |
| Failed hydration error and detached descendant retention                                   | `conditional-hydration-contracts.test.ts`                                           |

The two retention tests run real V8 garbage collection through Node's `node:v8` and `node:vm`, cross job boundaries before collection, and inspect `WeakRef` targets. They keep the branch mounted to distinguish timely release from eventual branch disposal. They require the repository's supported Node runtime; they do not run in a browser. The detached-node case checks unnecessary retention after removal, not support for rerendering an externally modified DOM tree. Its live child-node collection is refreshed after removal so that jsdom's lazy collection cache does not retain the removed node itself.

## Survivor ledger

IDs below refer to this campaign's report and are not stable across source edits. Reassess these conclusions whenever input validation, cleanup behavior, or revision consumers change. These mutations remain included in the raw score. Equivalent observable behavior does not imply identical allocation or execution cost.

| File / mutant IDs                  | Mutation                                                                 | Why current public behavior is unchanged                                                                                                                                                                                                                                                                                                        |
| ---------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `compiler/targets/client.ts`:30–33 | Change the choice between `renderableChildren(node)` and `node.children` | Their only difference is removal of empty text nodes. The parser creates nonempty text; whitespace normalization preserves a nonempty static segment or an expression's original slice; HTML normalization and constant-branch removal introduce no empty text. The validated public compilation pipeline therefore supplies the same children. |
| `compiler/targets/client.ts`:40    | Assume a component has one child                                         | IR validation rejects components without exactly one renderable root before lowering. The condition is already true for accepted components.                                                                                                                                                                                                    |
| `runtime/conditional.ts`:64        | Always inspect the root-node index after `textAt`                        | When no materialization occurred, this only searches and reassigns the same root node.                                                                                                                                                                                                                                                          |
| `runtime/conditional.ts`:169       | Seed `newlyHydrated` with an extra string                                | Disposal attempts to delete that string from a set containing binding objects. It cannot remove a real binding. There is an extra array entry and set operation.                                                                                                                                                                                |
| `runtime/conditional.ts`:181       | Always dispose the successful hydration handle during rollback           | The real boundary factory only invokes the binder after successful location. Missing handles are skipped; other location errors throw before scheduling. An error result cannot reach this callback through the actual runtime.                                                                                                                 |
| `runtime/conditional.ts`:193       | Decrement rather than increment the revision                             | Consumers only track a change and discard the value. Both directions notify identically, including symmetric numeric precision limits.                                                                                                                                                                                                          |
| `runtime/conditional.ts`:226       | Omit the empty-hydration early return                                    | The subsequent binding list is empty, interactive binding is disabled, and the same pending set is cleared. Only unnecessary traversal and allocation are added.                                                                                                                                                                                |
| `runtime/conditional.ts`:240       | Use a string entry when there is no pending set                          | Calling the string throws inside a catch that already preserves the original failure. No binding or cleanup runs; the original error is rethrown. This adds an internal exception allocation.                                                                                                                                                   |

The ref-cleanup registration guard and the root-index guard are deliberately absent from this survivor ledger: their mutations can change teardown event behavior or retain detached nodes, and the added tests detect them. Similarly, pending rollback removal is checked through actual error-object collection, not classified as equivalent merely because the displayed DOM matches.

## Recorded campaign

With the same 236 source mutations, the review follow-up increased detection from 191 to 225: the raw score changed from 80.93% to 95.34%, survivors from 32 to 11, and uncovered mutations from 13 to zero. There were no timeouts or mutation errors. All 11 survivors are accounted for above and remain in the denominator. These numbers describe this focused campaign, not whole-library mutation coverage.
